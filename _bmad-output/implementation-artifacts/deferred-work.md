## Deferred from: code review of 1-5-add-make-migrate-state-driver-with-applied-marker-file (2026-05-11)

- **(MED → driver hardening, post-Epic-1)** [`scripts/run-migrations.sh:84`](scripts/run-migrations.sh#L84) — non-atomic marker append: if the process is killed (SIGINT, OOM, system shutdown) between successful migration body and `printf '%s\n' "$name" >> "$marker"`, the migration is applied but unmarked, so the next run re-executes it. Per-script idempotency contract (script header lines 6-13) is the documented safety net, so any migration that violates idempotency is the real bug. Future hardening options: write the marker via temp+`mv`, or `trap` SIGINT/SIGTERM around the critical section. Out of scope for Story 1.5 (canonical body is byte-for-byte spec-mandated). Surface when the first non-idempotent migration body is contemplated.
- **(LOW → driver hardening, post-Epic-1)** [`scripts/run-migrations.sh:78-84`](scripts/run-migrations.sh#L78-L84) — no concurrency lock on the marker file. Two parallel `make migrate-state` invocations (e.g., two operators racing, or a CI run + a local run on the same checkout) can both pass the `already_applied` check, both execute the migration body, and both append duplicate marker lines. The Terraform backend usually has its own state lock; the driver does not. Single-operator design is intentional per the spec but is not stated in the script header. Future hardening: add `flock` on the marker (or `mkdir`-based mutex on a sibling lockfile). Surface if CI ever runs `make migrate-state`.
- **(LOW → driver hardening)** [`scripts/run-migrations.sh:62`](scripts/run-migrations.sh#L62) — marker tolerance: `grep -Fxq -- "$1" "$marker"` requires exact full-line match. A marker hand-edited on a CRLF-normalising filesystem (rare today) or with trailing whitespace will silently fail the membership test, the migration re-runs, and the marker accumulates duplicate entries with mixed line endings. Low likelihood (marker is gitignored, machine-written) but no guard exists. Future hardening: `tr -d '\r' < "$marker" | grep -Fxq ...`, or canonicalise the marker once at start.
- **(LOW → driver hardening)** [`scripts/run-migrations.sh:50-53`](scripts/run-migrations.sh#L50-L53) — `find` exit code is lost inside process substitution `< <(find ... | sort)`. Only `sort`'s exit code is observable, and `sort` exits 0 with no input. If `find` itself fails (permission denied on a sub-traversal), the helper silently emits "no migration scripts found, skipping" in a tree that actually has pending migrations. Rare with `-maxdepth 1` and a small directory. Future hardening: switch to `mapfile -t scripts < <(find ... | sort)` with explicit error capture, or `find ... -print0` + `read -d ''` paired with `PIPESTATUS` inspection.
- **(LOW → driver UX)** [`scripts/run-migrations.sh:21,28,46,88`](scripts/run-migrations.sh#L21-L88) — driver-reserved exit codes 1 and 2 collide with arbitrary migration-script exit codes. A caller (Make, CI step, downstream wrapper) cannot distinguish "driver rejected input" (rc=2 bad args / not-a-dir, rc=1 missing `.terraform/`) from "migration body returned 1 or 2." Acceptable today (Story 1.4's 001 scripts exit 0 only). Future convention: reserve a high-range exit code (e.g., 70+ per `sysexits.h`) for driver-originated errors and pass through script codes verbatim — or document the collision explicitly in the script header.
